# Контент-паки платформ

Каждый `*.yaml` в этом каталоге (включая подкаталоги) — пак одной платформы. Пак — данные,
а не код: добавление платформы или проверки не требует релиза агента. Файл на версию
(`ubuntu-server-1.0.0.yaml`); старые версии не удаляются — результаты прогонов привязаны
к версии пака, и без неё прошлый отчёт нельзя воспроизвести.

Каталог можно переопределить переменной `PACKS_DIR`. Битый пак — ошибка с именем файла
и причиной, а не тихий пропуск.

## Формат

```yaml
pack: ubuntu-server             # id: a-z, 0-9, дефис
version: 1.0.0                  # MAJOR.MINOR.PATCH
maturity: baseline              # inventory | draft | baseline | full | certified
verified_on: ["Ubuntu 22.04.4"] # обязательно для baseline/full/certified
tags: [linux-server, debian-family, ubuntu]   # класс → семейство → продукт
transport: local                # local | ssh
asset_type: linux-server        # необязательно

detect:                         # как распознать платформу (все условия должны совпасть)
  - probe: { type: file_kv, path: /etc/os-release, key: ID, separator: equals }
    equals: ubuntu              # либо regex: "..."

checks:
  - id: ssh.max_auth_tries      # категория.ключ
    title: Ограничить число попыток аутентификации
    probe: { type: file_kv, path: /etc/ssh/sshd_config, key: MaxAuthTries, default: "6" }
    assert: { op: lte, value: 4 }
    severity: medium            # critical | high | medium | low | info
    remediation: "MaxAuthTries 4 в /etc/ssh/sshd_config"
    refs: [{ source: "CIS Ubuntu 22.04", id: "5.1.x" }]
    control: AUTH-ATTEMPTS-LIMITED
```

## Уровни зрелости (`maturity`)

| Уровень | Смысл | Проверки | `verified_on` |
|---|---|---|---|
| `inventory` | Платформа распознаётся, список ПО собирается; **оценка не выставляется** (score пуст, а не 100 %) | только пусто | — |
| `draft` | Проверки написаны по документации, на реальном оборудовании **не запускались** (проверены на образцах вывода) | есть | пусто допустимо |
| `baseline` | Проверки **подтверждены на реальном оборудовании**; покрытие платформы частичное | есть | **обязательно**: на чём именно |
| `full` | Полный набор проверок платформы | есть | обязательно |
| `certified` | `full` + сверено вторым экспертом | есть | обязательно |

Валидатор отклоняет пак, который называет себя `baseline`+ без `verified_on`, и `inventory` с проверками:
уровень должен честно отражать, что реально проверено.

## Критичность (`severity`) и методики ФСТЭК

Шкала `critical | high | medium | low` совпадает по названиям с уровнями из
«Методики оценки уровня критичности уязвимостей программных,
программно-аппаратных средств» (ФСТЭК России, 30.06.2025). На неё ссылается
п. 3.4.3 «Методики анализа защищённости ИС» от 25.11.2025. Но это **не одно и то же**:

| | Методика от 30.06.2025 | `severity` в паке |
|---|---|---|
| Что оценивается | уязвимость ПО (идентификатор в БДУ/CVE) **на конкретной ИС** | нарушение конфигурации, **одинаково для всех активов** |
| Как | V = Icvss × Iinfr × (Iat + Iimp); Icvss — базовая оценка CVSS 3.1 от вендора | экспертная оценка автора пака |
| Уровни | V > 8 — критический; 5 ≤ V ≤ 8 — высокий; 2 ≤ V < 5 — средний; V < 2 — низкий | те же четыре названия (+ `info` — только для сведений, в методике нет) |

Поэтому `severity` — это **уровень опасности нарушения по оценке автора пака**,
а не рассчитанный уровень критичности V. Для нарушения конфигурации нет
CVSS-оценки вендора: Icvss пришлось бы считать калькулятором ФСТЭК. Iinfr
(значимость ИС, доступность из интернета) зависит от актива и в паке известен
быть не может. Честная формулировка в отчёте: «уровень опасности по оценке
пака», а не «уровень критичности по методике ФСТЭК».

Чтобы значения были сопоставимы с методикой, выбирайте `severity` по тому, какой
уровень вышел бы у типового актива:

- `critical` — удалённая эксплуатация без учётных данных или прямой путь к
  полному захвату узла (пустые пароли по SSH, privileged-контейнер);
- `high` — компрометация при минимальном дополнительном условии: подбор пароля,
  доступ из сети, уже захваченный контейнер. Сюда же относится отсутствие
  механизма, без которого атаку не обнаружить (аудит);
- `medium` — ослабление защиты, которое само по себе не даёт доступа, но
  облегчает атаку (длина пароля, TLS ниже 1.2, лимиты ресурсов);
- `low` — гигиена и эшелонирование (NTP, X11-форвардинг, лимит CPU).

Что следует из методик для отчёта (справочно, не правило движка):

- п. 3.4.4 методики от 25.11.2025 — уязвимости критического и высокого уровня
  заказчик устраняет обязательно;
- средний и низкий уровень (п. 3.4.5) — после экспертной оценки
  эксплуатируемости;
- ориентир сроков из методики от 30.06.2025: критический — до 24 часов,
  высокий — до 7 дней, средний — до 4 недель, низкий — до 4 месяцев.

## Несколько паков на один актив

Хосту может подходить несколько паков сразу: ОС + Docker + СУБД. Агент выполняет **все** подошедшие (`detect`)
и отправляет одним запросом (`packs: [{id, version, probe_results}, …]`): один прогон — один снимок и общая оценка.
`--pack <id>` ограничивает прогон одним паком. Если пак пропал с хоста (например, удалён Docker), его проверок
в текущем состоянии актива больше нет, история прогонов сохраняется. Один и тот же пак дважды в запросе — ошибка 422.
Ответ `/api/ingest` содержит итоги по каждому паку (`packs`) с его `maturity`.

## Пробы (только чтение)

| type | Параметры | Результат |
|---|---|---|
| `file_kv` | `path`, `key`, `separator` (whitespace/equals), `default`, `match` (first/last), `ignore_case`, `follow_include` | значение параметра; с `follow_include: true` раскрываются `Include` (sshd_config.d/*.conf) |
| `file_regex` | `path`, `pattern` | группа 1 (или совпадение); нет совпадения — пусто |
| `file_stat` | `path`, `field` (mode/owner/group/uid/gid) | права/владелец без чтения содержимого |
| `cmd_regex` | `cmd` (argv, без shell), `pattern` | группа 1 (или совпадение) |
| `cli_config` | `cmd` (show/display, `/export`, `… print`), `match`, `section`, `require` | совпавшая строка конфигурации устройства. Ошибка устройства (`% …`) и отсутствие `require` в ответе — проба не выполнилась (иначе при нехватке прав все проверки «параметра нет» ложно прошли бы) |
| `service_state` | `service`, `field` (active/enabled) | состояние службы systemd |
| `pkg_version` | `package` | версия пакета; пусто — не установлен |
| `cmd_foreach` | `list_cmd`, `item_cmd` (элемент — последним аргументом), `pattern`, `max_items` | **число** элементов списка, вывод которых подходит под `pattern`; пустой список — 0; сбой любой команды — проба не выполнилась, а не 0 |
| `first_of` | `probes` (2–5 проб, без вложенного `first_of`) | результат первой пробы, нашедшей значение (например, `ufw status`, иначе файл конфигурации) |

Агент выполняет только эти пробы и только команды из собственного белого списка.
Чтение `/etc/shadow` и ключей файловыми пробами запрещено (для прав — `file_stat`).

## Утверждения (`assert`)

`eq`, `ne`, `in`, `not_in` (список), `lt`, `lte`, `gt`, `gte` (число), `regex`, `exists`, `absent`,
`mode_within` (права файла не шире заданных, значение — восьмеричная строка в кавычках: `"640"`).

Для прав файлов используйте `mode_within`, а не `lte`: `604` численно меньше `640`, но шире по правам.
Проба ничего не нашла, а оператор не `exists`/`absent` — статус `error`, а не `fail`
(«нечего сравнивать»).

## Ловушки YAML

- `no`, `yes`, `on`, `off` без кавычек — булевы значения, а не строки. Всегда `"no"`, `"yes"`.
- Права файлов и версии — строки в кавычках: `0640` YAML читает как восьмеричное число 416.
- Регулярные выражения — в одинарных кавычках (`'^\s*(\d)'`), чтобы обратные слэши не обрабатывались YAML.
