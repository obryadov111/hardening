## 0 · Главное

Задача плана звучала как «перенести и получить идентичные результаты». При разборе старого кода выяснилось, что **идентичность невозможна и не нужна**: у старых сборщиков есть реальные дефекты, из-за которых инструмент аудита **ложно засчитывал нарушения как выполненные**. Переносить их значило бы тиражировать ошибки в новую архитектуру. Поэтому этап сделан иначе:

- результаты нового пака и старого агента сравниваются на одном хосте по каждому правилу;
- расхождения допустимы **только** там, где старая логика неверна, и каждое зафиксировано тестом с точной парой статусов и причиной;
- любое непредусмотренное расхождение — провал теста.

| Показатель | Значение |
|---|---|
| Проверок в паке | **12** из 14 прежних правил |
| Тестов бэкенда | **152** (было 123, **+29**) |
| Тестов агента | **82** (было 69, **+13**) |
| Регрессионных сценариев «старый агент ↔ пак» | 16 (5 идентичных + 7 задокументированных расхождений + проверки состава) |
| Прогон на реальном хосте | Ubuntu 24.04.4: 9 из 12 совпали, 3 расхождения — ровно задокументированные |
| Проверка стенда мутациями | 4 намеренные порчи пака, все пойманы (одна сначала выжила — закрыта новым сценарием) |
| Фронтенд | без изменений |

## 1 · Дефекты старого агента

Все проверены на реальной Ubuntu 24.04 (этот сервер) и закреплены тестами.

| # | Проверка | Что делал старый агент | Последствие | Что делает пак |
|---|---|---|---|---|
| 1 | `ssh.permit_root_login` | Считал значением по умолчанию `no` | **Ложный pass.** У OpenSSH умолчание — `prohibit-password` (вход root по ключу разрешён). На этом хосте: старый «pass (no)», реально `prohibit-password` | Умолчание `prohibit-password` → **fail**, пока не задано `no` явно |
| 2 | `password_policy.lockout_on_failure` | Блокировка «включена», если файл `faillock.conf` **непустой**; а также при любой подстроке `pam_faillock` в `common-auth`, **включая закомментированную** | **Ложный pass.** На этом хосте `faillock.conf` — 62 строки, все комментарии, `pam_faillock` в PAM не подключён: блокировки нет, а старый агент писал «true» | Ищет **действующую** (не закомментированную) строку `pam_faillock`/`pam_tally2` в PAM-стеке |
| 3 | `ssh.*` (все пять) | Не понимал `Include`; брал **последнее** вхождение параметра (sshd берёт первое); читал строки внутри `Match` как глобальные | Неверное значение на любой Ubuntu 22.04+, где настройки лежат в `sshd_config.d/*.conf` (на этом хосте `Include` есть) | `follow_include`, первое значение побеждает, `Match` не учитывается |
| 4 | `ssh.max_auth_tries` | Требовал **ровно** `4` | Более строгое значение (3) считалось нарушением | `≤ 4` |
| 5 | `password_policy.pass_max_days` | Требовал **ровно** `90` | Срок 60 дней (строже) считался нарушением | `≤ 90` |
| 6 | `password_policy.pass_min_len` | Требовал **ровно** `14` | Длина 16 (строже) считалась нарушением | `≥ 14` |
| 7 | `firewall.default_incoming_policy` | Требовал строку `deny`; в резервном файле `/etc/default/ufw` запрет записывается как `DROP` | Правильно настроенный хост считался нарушителем. На этом хосте: старый «fail (drop)», реально это запрет | `deny`, `reject` и `drop` — все запрещают входящие |

Ложные **pass** (пп. 1, 2) опаснее ложных fail: аудит показывает «всё хорошо» там, где защиты нет. Ложные fail (пп. 4–7) шумят, но не скрывают риск.

## 2 · Как проверялось

### 2.1 Регрессионный стенд (`test_ubuntu_pack_regression.py`)

`FakeHost` моделирует хост (файлы и команды) и даёт два интерфейса: прежний (`read_file`/`run` для `collector.py`) и транспорт проб. Один и тот же хост прогоняется обоими путями; статусы сравниваются по 12 общим правилам. Правила старого агента берутся **из настоящей миграции с сидом**, не переписываются вручную.

- **Идентичные сценарии (5)** — где старая логика верна: эталонно защищённый хост, полностью незащищённый, `ufw` без root с откатом на файлы, голый контейнер, `ufw` включён по файлу. Пути обязаны совпасть полностью.
- **Расхождения (7)** — каждое с точной парой (статус старого, статус пака) и причиной: строгие значения; умолчание `PermitRootLogin`; `faillock.conf` из комментариев; закомментированный `pam_faillock`; политика `reject`; `DROP` в файле; `Include` + первое значение + `Match`.
- **Страховки:** сценарии в сумме дают все три исхода (`pass`, `fail`, `error`); направления расхождений — только известные (`pass→fail` лишь для двух правил с ложными прохождениями); пак содержит ровно 12 правил и **ни одного нового кода**; критичность каждой проверки равна критичности исходного правила.

### 2.2 Мутационная проверка самого стенда

Тест, который никогда не падает, ничего не доказывает, поэтому пак намеренно портился:

| Мутация | Результат |
|---|---|
| `max_auth_tries`: `≤ 4` → `= 4` | поймана |
| убран откат `ufw` на файл конфигурации | поймана |
| умолчание `PermitRootLogin` снова `no` | поймана |
| регулярка блокировки снова ловит комментарии | **выжила** → в стенд добавлен сценарий «`pam_faillock` закомментирован» → теперь поймана |

## 3 · Что добавлено в движок проб

### 3.1 `file_kv` с `follow_include`

Раскрывает директивы `Include` так же, как sshd: маска, относительные пути от каталога файла, файлы по маске в лексическом порядке, подстановка на месте директивы. **Первое найденное значение побеждает.** `Match` действует до конца своего файла и не «протекает» во включаемый следом (как в sshd). Ограничения безопасности: глубина 5, не более 50 файлов, самовключение завершается; запрещённые политикой файлы не читаются даже через `Include` или символическую ссылку; нечитаемый включаемый файл не отменяет остальные.

### 3.2 Проба `first_of`

Несколько источников одного значения по порядку, берётся первый нашедший. Так старый агент получал состояние `ufw`: `ufw status` (нужен root), иначе файл конфигурации. Отличает «источники прочитаны, значения нет» (`найдено`, значение пусто) от «ни один источник недоступен» (проба не выполнилась). Вложенность запрещена; для транспорта `ssh` локальные и модифицирующие пробы внутри `first_of` отклоняются при загрузке пака.

## 4 · Метаданные результатов и интерфейс

**Проблема.** Интерфейс берёт название, код и критичность правила через `LEFT JOIN hardening_rules`. У результатов пака строки правила нет — колонки остались бы пустыми.

**Решение.** Миграция `b7d2e4f18c63`: `title`, `severity`, `remediation` сохраняются **в самой записи результата** (снимок на момент прогона), `evidence` — и в текущем состоянии (`hardening_checks`), а не только в истории. API читает `COALESCE(r.…, hc.…)`. Плюс: отчёт за прошлый период не зависит от последующих правок пака. Все колонки `nullable`, прежний путь не затронут.

Новые поля ответа `/hardening`: `evidence`, `pack {id, version}`, `rule.remediation`. **Фронтенд менять не пришлось**: он уже читает `rule.title`, `rule.rule_code`, `rule.severity`. Проверено тестами: результаты пака и результаты старого пути отображаются одинаково.
