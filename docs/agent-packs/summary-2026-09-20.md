### Самое важное из найденного

1. **Ложные «выполнено» в старом агенте** (проверено на реальном сервере): блокировка учётной записи считалась включённой при `faillock.conf` из одних комментариев; вход root по SSH считался запрещённым по умолчанию, хотя у OpenSSH умолчание разрешает вход по ключу; `Include`, порядок значений и блок `Match` разбирались неверно.
2. **Опасность при нехватке прав на сетевом устройстве:** Cisco отвечает `% Invalid input…` вместо конфигурации, и все проверки «параметра нет» ложно проходили бы на пустом выводе. Теперь такая проба даёт `error`.
3. **Числовое сравнение прав файлов некорректно** (`604` численно меньше `640`, но шире по правам): добавлен побитовый оператор `mode_within`.
4. **В CI бэкенда падали тесты на `main`** ещё до работ (нет `pythonpath` для pytest): исправлено.

### Проверка чтения существующих данных новым кодом

Прямое чтение боевой БД через скрипт в работающем контейнере **было отклонено автоматическим контролем прав** (как чтение production-данных); я не стал его обходить. Вместо этого та же проверка выполнена **на восстановленной копии бэкапа** (снятого до выкатки), с теми же миграциями и тем же кодом:

- миграции применились на копии реальных данных без ошибок;
- новая выборка `/hardening` возвращает **все 101 результат** (по каждой организации число совпадает с таблицей);
- у 3 результатов нет названия и критичности — **это старые демо-данные** (`srv-1`, `srv-3`) с пустым `rule_id`; сравнение со **старым** запросом на той же копии показало те же 3 из 101, то есть это не регрессия.

### Что НЕ проверялось на живой системе (честно)

- **Живой ingest от агента нового формата не выполнялся.** Для этого нужен ключ агента конкретной организации, а создание ключей и запись тестового актива меняют боевые данные — это выходило за рамки поручения. Новый путь проверен тестами (сквозные сценарии агент → сервер), на копии данных и запуском агента на этом хосте в режиме `--dry-run`.
- **Интерфейс (фронтенд) в браузере не открывался** — он не менялся; чтение данных проверено на уровне API-выборки.
- **Агент на хостах не установлен и расписания нет** (как и до этого). Обычный режим агента работает по-старому; режим `--use-packs` пока запускается вручную.

## 5 · Откат

Данные не менялись, добавлены только nullable-колонки, поэтому откат кода безопасен и **без** отката миграций (старый код новые колонки не читает).

```bash
cd /home/hardening/hardening
# 1) вернуть прежний код бэкенда
docker stop hardening_backend && docker rm hardening_backend
docker run -d --name hardening_backend --network bridge -p 8000:8000 \
  --env-file ./src/backend/.env --restart unless-stopped hardening-backend:pre-packs
docker network connect diplom-hardening_default hardening_backend

# 2) (необязательно) откатить схему: потеряются только результаты пак-проверок
docker run --rm --network diplom-hardening_default --env-file ./src/backend/.env \
  hardening-backend:packs alembic downgrade 5bbca4cdfbaa

# 3) (крайний случай) полное восстановление из дампа
#    ~/backups/app_db-pre-packs-<метка>.sql  (метка — в ~/backups/.last-deploy-ts)
```

Для отката `PACK_SIGNING_KEY` из `.env` убирать не обязательно: старый код его игнорирует. Копия прежнего `.env` — в `~/backups/env-pre-packs-<метка>.bak`.

## 9 · Безопасность и эксплуатация

- **Токен GitHub.** Выданный вами классический токен остаётся действующим, а его права шире нужных (`admin:org`, `delete:packages`, `workflow` и другие). **Его нужно отозвать вручную**: GitHub → Settings → Developer settings → Personal access tokens. Через API отозвать сам токен нельзя. Он использовался только для PR, issues и чтения статуса CI, на диск не записывался.
- **`gh` (GitHub CLI)** установлен в `~/.local/bin/gh`, без входа в аккаунт; сам по себе ничего не делает.
- **Бэкапы** (`~/backups/`) содержат полную БД, включая хэши паролей пользователей: каталог 700, файлы 600; храните и удаляйте осознанно.
- **`.env`** содержит новый секрет `PACK_SIGNING_KEY`; файл в git не отслеживается (проверено), права 600.
- **Как запускать агент на хосте** (пока вручную):

```bash
export HARDENING_AGENT_API_KEY=<ключ агента организации>
export HARDENING_PACK_KEY=$(cat ~/.config/hardening-agent/pack.key)   # ключ проверки подписи паков
python3 collector.py --api-url http://<бэкенд>:8000 --environment prod --use-packs
```
