### Про критерий «паки добавляются только данными»

План этапа гласил: два новых пака должны добавляться без единой правки кода агента и бэкенда. **Выполнено частично, и это важный результат:**

| Пак | Только данными? | Что потребовалось в коде |
|---|---|---|
| `astra-linux` | ✅ **да** | ничего (кроме общей поддержки нескольких паков) |
| `docker` | ❌ | новая проба `cmd_foreach`: «список → команда по каждому элементу» |
| `cisco-ios` | ❌ | защита от ложных прохождений при нехватке прав (раздел 2) |

Обе правки — **общие возможности движка**, а не код под конкретную платформу: `cmd_foreach` пригодится любому «списку с проверкой каждого элемента» (контейнеры, интерфейсы, пользователи), защита пробы `cli_config` — любому сетевому устройству. Это ожидаемая цена первого пака нового класса; цель по-прежнему в том, чтобы каждый следующий пак такого класса добавлялся уже без кода.

## 1 · Несколько паков на один актив

**Проблема.** До этапа 2 один прогон = один пак. Хост с Ubuntu и Docker должен был проверяться дважды, а каждый ingest **полностью перезаписывал** текущее состояние актива — второй пак затирал бы первый. Два ingest'а на прогон дали бы ещё и два частичных снимка в истории, тренд `compliance_score` на дашборде превратился бы в кашу.

**Решение.** Один запрос — все паки прогона.

```json
{ "packs": [
    { "id": "ubuntu-server", "version": "1.0.0", "probe_results": { … } },
    { "id": "docker",        "version": "1.0.0", "probe_results": { … } } ] }
```

| Аспект | Поведение |
|---|---|
| Снимок и оценка | Один прогон — **один** снимок и общая оценка по всем проверкам всех паков |
| Итоги по пакам | Ответ содержит `packs: [{id, version, maturity, total, passed, failed, errors}]` |
| Агент | Выполняет **все** подошедшие паки (раньше при нескольких — ошибка «укажите `--pack`»); теги паков объединяются без повторов; `--pack <id>` ограничивает прогон одним |
| Пак пропал с хоста | Его проверок в текущем состоянии актива больше нет (например, удалили Docker); история прогонов сохраняется — проверено тестом |
| Один пак дважды | `422` **без побочных записей** (все паки разрешаются до записи в БД) |
| Неизвестный пак/версия | `422`, как и раньше |
| Старый формат | `pack` + `probe_results` работает и **комбинируется** со списком `packs` |
| Сырые результаты | Хранятся в `agent_collections.collected_data` по каждому паку (для перепрогона по новой версии) |

**Проверено на реальном хосте** (`--dry-run`, Ubuntu 24.04.4 с работающим Docker): агент распознал `ubuntu-server` и `docker`, `astra-linux` — нет; собрал один payload с двумя прогонами (13 проб), теги объединил. Docker: «0 из 3» контейнеров привилегированных.

## 2 · Главная находка: ложные прохождения при нехватке прав

При составлении сценариев для Cisco стало видно опасность: у read-only учётки часто нет прав на `show running-config`, и IOS отвечает `% Invalid input detected at '^' marker.` вместо конфигурации (код возврата при этом нулевой). Дальше проба «параметра нет» видит пустой вывод, и **все проверки вида `absent` ложно проходят**: «SNMP community public отсутствует», «HTTP-сервер выключен», «нет `enable password`» — на устройстве, которое вообще не удалось прочитать. Это тот же класс ошибок, что нашёлся в старом агенте на этапе 1 (см. [Этап 1 — пак ubuntu-server, подробный отчёт](stage1-report.md), раздел 1): аудит показывает «всё хорошо» там, где ничего не проверено.

**Защита в пробе `cli_config`** (два независимых слоя):
1. **Ошибка устройства.** Если первая непустая строка ответа — `% …` (так IOS сообщает `Invalid input`, `Authorization failed`, `Incomplete command`), проба **не выполнена** → статус `error`.
2. **`require`.** Необязательный признак настоящего вывода. Для `running-config` это завершающая строка `end`: обрыв, пустой ответ или чужой текст → проба не выполнена → `error`.

Проверено 5 сценариями: 3 разных сообщения об ошибке, пустой ответ и обрыв конфигурации — **ни один не даёт `pass`, все `error`**. Мутационная проверка: без `require` падают тесты (обрыв), без обработки `% …` вместе с `require` — падают пять. Ту же защиту получает любой будущий сетевой пак.

## 3 · Пак `docker` (baseline)

Перенос последнего «настоящего» правила старого агента: `docker.no_privileged_containers`.

- **Признак Docker** — сокет `/var/run/docker.sock`.
- **Проба `cmd_foreach`:** `docker ps -q` → для каждого id `docker inspect --format {{.HostConfig.Privileged}}` → **число** привилегированных. Проверка `= 0`.
- **Пустой список — 0** (контейнеров нет, нарушать нечего — как у старого агента).
- **Сбой любой команды — проба не выполнена (`error`), а не 0.** Иначе недоступный docker выглядел бы как «привилегированных контейнеров нет» (тот же класс ложных прохождений). Регрессионный тест сравнивает пак со старым агентом на трёх состояниях хоста; ошибка docker сохраняет семантику «нет факта → error».
- **Белый список агента для `docker`** — только `ps -q` и `inspect --format {{.HostConfig.Privileged}} <id>`. `run`, `exec`, `rm`, `ps -a` и **любое другое поле `inspect`** (например, `{{.Config.Env}}` с переменными окружения контейнера, то есть секретами) отклоняются. Каждый id проходит проверку **отдельным вызовом**, а не подставляется в общую строку (проверено на попытке инъекции `abc; rm -rf /`).
- **Подтверждён на реальном оборудовании:** `verified_on: Docker Engine 29.3.1 на Ubuntu 24.04.4 LTS`. Проверка одна, поэтому в паке отмечено: baseline здесь — «подтверждено на оборудовании», а не «полный набор».

## 4 · Пак `cisco-ios` (draft)

11 проверок по SSH (транспорт этапа 0), команда `show running-config`.

| Проверка | Смысл | Критичность |
|---|---|---|
| `cisco_ios.service_password_encryption` | шифрование паролей в конфигурации | medium |
| `cisco_ios.enable_secret_used` | пароль привилегированного режима через `enable secret` | high |
| `cisco_ios.enable_password_absent` | нет `enable password` (обратимый/открытый) | high |
| `cisco_ios.aaa_new_model` | включена модель AAA | high |
| `cisco_ios.snmp_default_community_absent` | нет community `public`/`private` | high |
| `cisco_ios.ssh_version2_only` | SSH версии 2 | medium |
| `cisco_ios.http_server_disabled` | встроенный HTTP-сервер выключен | medium |
| `cisco_ios.vty_telnet_disabled` | на линиях VTY не разрешён Telnet (`transport input telnet/all`) | high |
| `cisco_ios.vty_ssh_only` | на линиях VTY задан `transport input ssh` | high |
| `cisco_ios.vty_acl_set` | на VTY ограничен доступ по `access-class` | medium |
| `cisco_ios.ntp_configured` | настроена синхронизация времени | low |

**Почему `draft`, а не `baseline`.** Устройства нет. Пак проверен на **образцах вывода** (защищённая и слабая конфигурации, два формата баннера IOS и IOS XE, отказ по правам, обрыв), но на реальном оборудовании не запускался. Валидатор не даёт назвать такой пак `baseline` без `verified_on` — уровень честно отражает, что подтверждено. Повышение до `baseline` — после прогона на стенде с записью версий IOS.

**Что проверено тестами:** детект на IOS и IOS XE и его **отсутствие** на Junos, Linux, MikroTik и пустом ответе; защищённая конфигурация — все 11 `pass`; слабая — все 11 `fail`; Telnet в любом из блоков VTY ловится; проба выполняет **только** `show`-команды; секреты в свидетельстве маскируются (`enable password ***`, `snmp-server community ***` — ни хэша `0822455D0A16`, ни слова `public`).

**Известные ограничения** (записаны и в самом файле пака):
- Если в блоке `line vty` **нет** строки `transport input`, IOS применит умолчание платформы, и проверка Telnet этого не поймает; отчасти закрывает `vty_ssh_only`, но он проверяет наличие хотя бы одного блока с ssh, а не всех. Полное решение требует счётчика по блокам — в формате пока не выражается.
- SNMP: ищутся только `public`/`private` в открытом виде, не любые слабые значения.
- `show running-config` на уровне привилегий read-only учётки часто недоступен: без выданного уровня проверки получают `error` (см. раздел 2), а не ложный `pass`.
- Ссылки на источники — без номеров пунктов: конкретные бенчмарки не сверялись.

## 5 · Пак `astra-linux` (inventory)

**Только обнаружение, проверок нет — сознательно.** Astra Linux — сертифицированная ОС на основе Debian со своими механизмами защиты (режимы защиты, мандатный контроль целостности, мандатное управление доступом, замкнутая программная среда). Команды и параметры их проверки снимаются на реальном образе конкретной версии и редакции, по руководству вендора; писать их по памяти нельзя.

- **Детект** — по вхождению «astra» (без учёта регистра) в `ID`, `NAME` или `PRETTY_NAME` файла `/etc/os-release`, **а не** по точному `ID=astra`: точное значение для разных версий и редакций без образа не сверено. Проверено на четырёх вариантах файла и на Ubuntu, Debian, Fedora, ALT (не распознаются).
- **Что происходит на Astra:** платформа распознаётся, собирается список ПО (Astra на основе Debian — `dpkg` работает), проверок нет, **оценка не выставляется** (score пуст, а не «100 %»). Пак `ubuntu-server` на Astra **не применяется** (`ID` не `ubuntu`) — тест это фиксирует.
- **Единственный пак этапа, добавленный чистыми данными.**

## 6 · Формат: уровни зрелости стали строгими

Добавлен уровень **`draft`** и ужесточена валидация:

| Уровень | Смысл | Проверки | `verified_on` |
|---|---|---|---|
| `inventory` | только обнаружение; оценка не выставляется | **только пусто** (раньше не запрещалось) | — |
| `draft` | по документации, на оборудовании **не запускалось** | есть | пусто допустимо |
| `baseline` | подтверждено на оборудовании | есть | **обязателен** (раньше только для `full`/`certified`) |
| `full`, `certified` | полный набор; сверено вторым экспертом | есть | обязателен |

Смысл: уровень пака не может **завышать** проверенное. `verified_on` теперь означает «на каком оборудовании реально прогнано».
