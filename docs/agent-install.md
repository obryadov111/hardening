# Установка агента на объекте заказчика

## Что согласовать со службой безопасности заказчика

- **Сеть:** только исходящий HTTPS (`443/tcp`) к одному адресу — `audit.<домен>`. Входящих соединений нет,
  VPN не нужен. Если интернет только через прокси — адрес прокси.
- **Что делает агент:** только читает конфигурацию хоста по пакам, подписанным сервером (белый список команд,
  запрет чтения секретов: `/etc/shadow`, ключи SSH, кусты `SAM` и `SECURITY` реестра). Ничего не меняет.
- **Что уходит на сервер:** результаты проверок конфигурации, список установленного ПО, имя хоста, IP, ОС.
  Пароли, хэши, ключи и SNMP-community маскируются агентом и на сервер не попадают.
- **Права:** Linux — отдельный пользователь `hardening-agent` без входа, служба с ужесточением systemd;
  Windows — задача планировщика от SYSTEM (политика безопасности и аудита доступны только администратору).

## Ключ площадки и регистрация хостов

Ключ выдаётся не на хост, а на площадку (офис, ЦОД, сегмент) — один для всех её хостов, поэтому установку
можно раскатать штатными средствами: GPO, Ansible, образ ОС. При первом запуске агент регистрирует хост
(`POST /api/agent/enroll`) и получает **свой ключ хоста**; дальше работает только с ним:

- отчёт по ключу хоста сервер принимает только с именем этого хоста — ключ, вынутый с одного ПК, не позволяет
  подделать отчёты остальных;
- отозвать можно один хост (страница «Агенты» → «Хосты»), остальные продолжают работать;
- ключ площадки после регистрации не нужен: его срок или отзыв не затрагивают зарегистрированные хосты.
  На время массовой установки разумно выдать ключ с коротким сроком;
- ключ хоста хранится в `host.json` каталога состояния: Linux — `/var/lib/hardening-agent/<экземпляр>/`
  (0600, пользователь агента), Windows — `C:\ProgramData\HardeningAgent\` (доступ только SYSTEM и
  «Администраторы», агент снимает наследование прав);
- имя занято, пока хост на связи: вторая установка с тем же именем получит отказ. Имя хоста, который молчит
  больше 7 дней (переустановка ОС, замена ПК), новая установка занимает сама; сразу — после «Удалить
  регистрацию» в интерфейсе. Отозванный хост заново не регистрируется, пока регистрацию не удалят.

## Что выдаёт аудитор

1. Ключ площадки — интерфейс, «Агенты» → «Новый ключ площадки». Там же готовый файл настроек и команды.
2. Открытый ключ подписи паков — там же.
3. Отпечаток ключа сервера (`HARDENING_PIN_SHA256`) — его печатает `deploy/enable_https.sh` на сервере
   или агент: `python3 collector.py --api-url https://audit.<домен> --environment x --show-server-pin`.

Агент скачивается с сервера: `https://audit.<домен>/downloads/` (публикует аудитор командой
`deploy/publish_agent.sh`). Готовые команды с адресом, контрольной суммой и настройками — в интерфейсе,
страница «Агенты»: «Скачать агент» и «Новый ключ площадки». Новые ОС и проверки агент получает с сервера сам —
переустанавливать его нужно, только когда выходит новая версия самого агента.

## Linux (systemd)

```bash
curl -fsSLO https://audit.<домен>/downloads/hardening-agent-linux.tar.gz
echo "<SHA-256 из интерфейса>  hardening-agent-linux.tar.gz" | sha256sum -c
tar xzf hardening-agent-linux.tar.gz && cd hardening-agent
sudo deploy/install.sh                   # экземпляр local — этот хост
sudo nano /etc/hardening-agent/local.env # вставить файл настроек из интерфейса (одинаковый на всех хостах площадки)
sudo systemctl start hardening-agent@local.service && journalctl -u hardening-agent@local -n 30
sudo systemctl enable --now hardening-agent@local.timer   # ежедневно
```

Нужен системный Python 3 — только стандартная библиотека, без pip. Первый прогон регистрирует хост.
Для многих хостов — те же шаги в Ansible: архив, `install.sh`, файл настроек (шаблон), таймер.

## Windows

`hardening-agent.exe` — Python на хосте не нужен (собирается в CI, workflow **Windows packs**). PowerShell от
администратора:

```powershell
mkdir -Force "C:\Program Files\Hardening" | Out-Null; cd "C:\Program Files\Hardening"
Invoke-WebRequest https://audit.<домен>/downloads/hardening-agent.exe -OutFile hardening-agent.exe
(Get-FileHash hardening-agent.exe -Algorithm SHA256).Hash   # сверить с SHA-256 из интерфейса
# регистрация хоста: ключ площадки только в этой команде, на хосте он не сохраняется
& "C:\Program Files\Hardening\hardening-agent.exe" --api-url https://audit.<домен> --environment prod `
  --api-key <ключ площадки> --pin-sha256 "sha256//<отпечаток>" --enroll
setx /M HARDENING_PACK_PUBLIC_KEY "<открытый ключ>"
setx /M HARDENING_PIN_SHA256 "sha256//<отпечаток>"
# при прокси: setx /M HARDENING_PROXY "http://proxy.corp:3128"
# Register-ScheduledTask, а не schtasks /TR: PowerShell неправильно передаёт schtasks вложенные кавычки пути с пробелом
$action = New-ScheduledTaskAction -Execute "C:\Program Files\Hardening\hardening-agent.exe" `
  -Argument "--api-url https://audit.<домен> --environment prod --use-packs"
Register-ScheduledTask -TaskName "Hardening agent" -Action $action -Trigger (New-ScheduledTaskTrigger -Daily -At 03:00) `
  -User SYSTEM -RunLevel Highest -Force | Out-Null
Start-ScheduledTask -TaskName "Hardening agent"
```

Ключ хоста и очередь неотправленных прогонов — `C:\ProgramData\HardeningAgent\`. Ключ площадки не кладётся
в переменные среды: переменные машины может прочитать любой пользователь ПК. Открытый ключ паков и отпечаток
сервера не секретны.

Для сотен ПК — те же команды сценарием запуска компьютера в групповой политике (GPO, выполняется от SYSTEM):
`.exe` из общей папки домена, `--enroll`, задача планировщика. Готовый сценарий и пошаговая инструкция —
после проверки на тестовом домене.

## Проверка связи

```bash
curl -sS https://audit.<домен>/health                       # {"status":"ok"}
python3 collector.py --api-url https://audit.<домен> --environment x --show-server-pin  # совпадает с выданным
```

Прогон появляется в интерфейсе в «Сканированиях»; хост — на странице «Агенты» → «Хосты» со временем и адресом
последней связи.

## Если что-то не так

| Сообщение агента | Причина |
|---|---|
| `нужен https://` | в `HARDENING_API_URL` указан `http://` (допустим только `localhost`) |
| `сертификат сервера не прошёл проверку` | в сети заказчика TLS-инспекция или свой УЦ — `HARDENING_CA_FILE` с корневым сертификатом; либо время на хосте неверное |
| `открытый ключ сервера не совпал с закреплённым` | ответил не наш сервер (перехват, подмена DNS) — **остановиться и выяснить**; либо сервер сменил ключ, а отпечаток не обновлён |
| `Сервер недоступен … сохранён в очередь` (код 75) | нет связи; прогон будет дослан при следующем запуске (очередь — до 50 прогонов и 30 дней) |
| `HTTP 401 — Недействительный ключ агента` при регистрации | ключ площадки отозван или истёк — выдать новый |
| `ключ хоста отозван или регистрация удалена` | хост отозван или регистрация удалена в интерфейсе; с ключом площадки агент регистрируется заново сам; очередь сохраняется |
| `Хост … уже зарегистрирован и был на связи` | то же имя у другого работающего хоста — переименовать хост; если это переустановка — «Удалить регистрацию» |
| `Регистрация хоста … отозвана администратором` | хост отозван — регистрировать заново можно после «Удалить регистрацию» |
| `Подпись манифеста … неверна` | паки подписаны не тем ключом, что `HARDENING_PACK_PUBLIC_KEY`, — проверить ключ; не обходить |

## Изолированный сегмент (без связи с сервером)

Агент сохраняет прогон в файл (`--out report.json`), подписанный ключом хоста, а если хост не регистрировался, —
ключом площадки, с манифестами из файла
(`--manifests-file`). Файл переносится и загружается в интерфейсе: «Агенты» → «Отчёт агента из файла».
Подробнее — `docs/deploy-server.md`, раздел 6.
