# Развёртывание сервера для агентов из интернета

Сервер (сайт + бэкенд + PostgreSQL) стоит в одном месте — у аудитора: свой сервер, VPS в РФ или DMZ. Агенты
стоят у заказчиков в других сетях и городах. Агент **сам** обращается к серверу по HTTPS, к агенту никто не
подключается: от объекта заказчика нужен только исходящий доступ на `443` к одному адресу. VPN, белый IP
и входящие порты у заказчика не нужны.

```
 объект заказчика                         сервер аудитора (audit.<домен>)
 агент ── GET  /api/agent/manifests ──┐   nginx :443 (TLS, лимиты)
       └─ POST /api/ingest ───────────┼─► ├─ /api/agent/*, /api/ingest — для агентов (ключ агента)
 изолированный сегмент:               │   ├─ сайт и /api/* — для аудиторов (пароль + 2FA)
 агент --out → файл → интерфейс ──────┘   └─ бэкенд :8000 и PostgreSQL — только localhost
```

Схема, модель угроз канала и план работ — в vault: «Схема передачи данных агент — сервер через интернет».

## 1. Сеть и домен

1. **Белый IP.** WAN-адрес в роутере совпадает с адресом на 2ip.ru — белый. Не совпадает (CGNAT) —
   подключить у провайдера услугу «белый IP». На VPS он есть всегда.
2. **Статический или динамический.** Динамический тоже подходит, но тогда DNS-запись нужно обновлять
   скриптом через API регистратора (DDNS).
3. **Домен** (`.ru`/`.рф`, 200–700 ₽/год) и DNS-запись `A audit.<домен> → внешний IP`.
4. **Роутер** (если сервер дома или в офисе): проброс TCP `443` и `80` на сервер. `80` нужен только для
   выпуска сертификата Let's Encrypt и переадресации на HTTPS.

## 2. HTTPS

```bash
sudo deploy/enable_https.sh audit.<домен> <email> --staging   # пробный сертификат: проверить, что всё доходит
sudo deploy/enable_https.sh audit.<домен> <email>             # боевой
```

Скрипт:
- ставит `certbot`, получает сертификат ECDSA (проверка HTTP-01 через nginx фронтенда);
- ставит хук продления: копия сертификата для nginx в `/etc/hardening-tls`, перезагрузка nginx. Продлевает
  таймер certbot;
- переводит фронтенд в режим HTTPS (`deploy/frontend.env`, `deploy/nginx-tls.conf.template`): `80` —
  переадресация, `443` — сайт и агенты, TLS 1.2/1.3, HSTS;
- открывает `443` в ufw;
- печатает отпечаток ключа сервера для агентов (`HARDENING_PIN_SHA256`).

Ключ сертификата при продлении не меняется (`--reuse-key`): закреплённый в агентах отпечаток остаётся верным.
Меняете ключ (компрометация) — сначала раздайте агентам новый отпечаток вторым значением
(`HARDENING_PIN_SHA256=sha256//старый,sha256//новый`), потом меняйте.

Если провайдер закрывает входящий `80`, нужна проверка через DNS (certbot с плагином регистратора) — скриптом
не покрыто.

Проверка снаружи — с мобильного интернета, не из той же сети: `https://audit.<домен>/health` и
https://www.ssllabs.com/ssltest/. Если роутер не умеет NAT loopback, агенту на самом сервере пропишите домен
в `/etc/hosts` (`127.0.0.1 audit.<домен>`).

## 3. Что открыто в интернет

Сотрудники открывают сайт откуда угодно — из офиса, из дома, из командировки — без VPN и настройки
компьютера. Защита — обязательная 2FA, лимиты и fail2ban; без входа из интернета доступны только страница
входа и статика интерфейса.

| Путь | Кто | Защита |
|---|---|---|
| `/api/agent/manifests`, `/api/ingest` | агенты | ключ агента (на объект, со сроком действия, отзываемый); лимит 120 запросов/мин с адреса; тело ≤ 10 МБ |
| `/health` | все | только `{"status":"ok"}` |
| `/api/auth/login`, `/api/auth/verify-2fa` | аудиторы | лимит 10 запросов/мин с адреса; блокировка учётной записи после 5 неудач; fail2ban; код 2FA |
| сайт, остальные `/api/*` | аудиторы | вход с паролем и **обязательной 2FA**; CSP |
| бэкенд `:8000`, PostgreSQL `:5432` | — | только `127.0.0.1`, снаружи не видны |

**Обязательная 2FA** (`REQUIRE_2FA=true` в `src/backend/.env`, по умолчанию включена). Пользователь без 2FA
после входа по паролю попадает только на её подключение (и смену временного пароля); остальной API отвечает
`403`, пока 2FA не включена. Украденный пароль без телефона сотрудника данных не даёт. Потерял телефон и
резервные коды — 2FA сбрасывает суперадмин, при следующем входе пользователь подключает её заново.
`REQUIRE_2FA=false` — 2FA по желанию (стенд, закрытая сеть).

**fail2ban** (`sudo deploy/enable_fail2ban.sh`, конфигурация — `deploy/fail2ban/`): 10 неудачных входов
(неверный пароль или код 2FA, `429` на входе) за 10 минут — адрес блокируется на 1 час, повторно — дольше,
до недели. Журнал nginx берётся из systemd-journal (фронтенд запущен с `--log-driver journald`), бан — в
цепочке `DOCKER-USER`: опубликованные порты Docker обходят `INPUT` и ufw. Пути агентов не учитываются: за одним
NAT заказчика бывает сотня агентов. Без блокировки — сети компании и внешний адрес NAT офиса, иначе
ошибившийся паролем сотрудник заблокировал бы коллег:

```bash
# deploy/frontend.env
HARDENING_FAIL2BAN_IGNOREIP="192.168.0.0/24 203.0.113.10"
```

Проверка: `sudo fail2ban-client status hardening-login`; снять блокировку: `sudo fail2ban-client unban <IP>`.

**CSP** (`deploy/nginx/app.conf`): скрипты, стили и запросы — только со своего адреса, без встроенных
скриптов; скрипт, попавший в данные (имя актива, текст из отчёта агента), браузер не выполнит.

**Ограничение по сетям — по желанию.** Если заказчик требует, чтобы интерфейс открывался только из офиса
(например, госзаказчик), сайт, вход и API интерфейса закрываются для остальных адресов (`403`); пути агентов
остаются открытыми:

```bash
# deploy/frontend.env; применяется deploy/restart_frontend.sh
HARDENING_ADMIN_NETWORKS=all                              # открыт всем (рекомендуется вместе с 2FA)
HARDENING_ADMIN_NETWORKS="192.168.0.0/24 203.0.113.10"    # только офис и внешний адрес NAT офиса
```

- Внешний адрес NAT офиса нужен, когда сотрудник в офисе открывает сайт по доменному имени: роутер
  разворачивает запрос (NAT loopback), и он приходит с этого адреса. Подделать его извне по TCP нельзя.
- Не задано — частные сети (`10/8`, `172.16/12`, `192.168/16`), `deploy/nginx/admin-allow.conf`.
- Шлюз Docker (`172.17.0.1`) запрещён всегда: через `docker-proxy`, например по IPv6, запрос из интернета
  приходит в контейнер с его адреса.

Лимиты — `deploy/nginx/limits.conf`, пути и CSP — `deploy/nginx/app.conf`, сети — `deploy/nginx/admin-allow.conf`.
При превышении лимита ответ `429`: агент считает его временной ошибкой и досылает прогон позже из очереди.

## 4. Ключи

**Подпись паков — Ed25519.** У агентов только открытый ключ: подписать им нельзя, поэтому ключ, извлечённый
на объекте заказчика, не позволяет подделать паки для других.

```bash
docker run --rm hardening-backend:latest python -m app.commands.pack_signing_key
# PACK_SIGNING_ED25519_KEY=... → в src/backend/.env (секрет, не в git), затем deploy/restart_backend.sh
# HARDENING_PACK_PUBLIC_KEY=... → агентам; его же показывает интерфейс, страница «Агенты»
```

Старый общий ключ `PACK_SIGNING_KEY` (HMAC) оставлен на время перехода: сервер отдаёт обе подписи, а агент
с открытым ключом принимает только Ed25519. Когда все агенты переведены на открытый ключ, `PACK_SIGNING_KEY`
можно убрать.

**Ключи агентов** — интерфейс, страница «Агенты»: отдельный ключ на объект (площадку, сегмент), срок действия,
отзыв, время и адрес последнего обращения. Ключ показывается один раз, сервер хранит только SHA-256.

## 4а. Агент для скачивания

```bash
deploy/publish_agent.sh    # от пользователя, без sudo; нужен gh с доступом к репозиторию
```

Публикует в `deploy/generated/downloads/` (в контейнере nginx — `https://audit.<домен>/downloads/`, открыто без
входа, как и пути агентов): `hardening-agent-linux.tar.gz` (из коммита, не из рабочего каталога),
`hardening-agent.exe` (из последней успешной сборки CI **Windows packs** с тем же кодом агента) и
`version.json` — версии, SHA-256, адрес и отпечаток ключа сервера. Страница «Агенты» показывает ссылки,
суммы и готовые команды установки, а в настройки нового ключа подставляет адрес и отпечаток.

Когда публиковать: только при изменении `agent/` (новая проба, исправление агента) — после пуша и сборки
.exe в CI (~3 мин; если она ещё идёт, Linux публикуется, для Windows остаётся прежний файл — повторите).
Новые ОС и проверки на существующих пробах — это паки на сервере: агенты получают их при следующем прогоне.

## 5. Обязательно перед открытием в интернет

- SSH — только по ключам (`PasswordAuthentication no`), ufw: `22`, `80`, `443`; остальное закрыто.
- Пароль sudo — не короче 14 символов.
- Бэкапы БД (`pg_dump`) — по расписанию, копия вне сервера.
- Если сервер дома — он в отдельной ВМ: из интернета нельзя попасть на другие домашние устройства.

## 6. Изолированные сегменты

Нет связи с сервером — агент сохраняет прогон в файл, подписанный ключом агента:

```bash
python3 collector.py --api-url https://audit.<домен> --environment asu --use-packs \
    --manifests-file manifests.json --pack-public-key <открытый ключ> --out report.json
```

Манифесты для офлайн-запуска — `python -m app.commands.pack manifests --ed25519-key-file … --out manifests.json`
на сервере. Аудитор переносит `report.json` и загружает его на странице «Агенты» → «Отчёт агента из файла».
Сервер проверяет подпись по хранимому хэшу ключа: изменённый файл не будет принят. В снимке отмечено, что отчёт
перенесён файлом и чьим ключом подписан.

## 7. Государственные информационные системы

Если для аттестуемой ГИС требуется сертифицированная криптография, передача идёт через криптошлюз заказчика
(ViPNet, Континент, ГОСТ TLS) или файлом (раздел 6). Агент и сервер при этом не меняются.
